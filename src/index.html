Conventional Commits

La guía definitiva para escribir mensajes de commit que humanos y máquinas puedan entender.

💡 ¿Por qué es importante?

Escribir un mensaje de commit desordenado es fácil, pero mantener un proyecto a largo plazo no lo es. Conventional Commits ofrece una estructura ligera que permite:

  • Generar CHANGELOGs automáticamente.
  • Determinar el siguiente número de versión semántica (SemVer) sin intervención humana.
  • Ayudar a otros desarrolladores a entender la historia del proyecto rápidamente.

🚀 Semantic Versioning (SemVer)

Conventional Commits y SemVer van de la mano. La estructura de tu commit dicta cómo debe incrementar la versión de tu software.

MAJOR . MINOR . PATCH

Ejemplo: Si estás en la versión 1.0.0 y haces un commit tipo feat: ..., la siguiente versión será 1.1.0.

🧩 Anatomía del Mensaje

Pasa el ratón por encima de los componentes para entender su función.

feat (api) ! : añadir autenticación por token

El cuerpo y el pie del mensaje son opcionales y van después de una línea en blanco.

🏷️ Tipos de Commits

Selecciona una pestaña para ver los tipos básicos o la lista completa de la convención Angular.

BREAKING CHANGE MAJOR

Un cambio que rompe la compatibilidad. Se indica con ! después del tipo o con un pie BREAKING CHANGE:.

feat!: drop node 12 support
feat MINOR

Introduce una nueva característica al código (feature). Equivale a MINOR en SemVer.

feat: allow zoom on images
fix PATCH

Arregla un error (bug) en el código. Equivale a PATCH en SemVer.

fix: handle null user id

Aunque la especificación permite cualquier tipo, estos son los adoptados casi universalmente.

docs

Cambios que afectan únicamente a la documentación (archivos README, comentarios JSDoc, tutoriales), sin modificar el código funcional.

style

Cambios de formato que no afectan la lógica del código (espacios en blanco, indentación, puntos y coma faltantes). No confundir con estilos CSS.

refactor

Un cambio en el código de producción que no corrige errores ni añade funcionalidades, pero mejora la estructura o legibilidad.

perf

Cambios dedicados específicamente a mejorar el rendimiento del sistema (optimización de algoritmos, reducción de tiempos de carga).

test

Adición de pruebas unitarias o de integración faltantes, o corrección de pruebas existentes que no funcionaban correctamente.

build

Cambios que afectan al sistema de compilación o dependencias externas (ej. npm, maven, gradle, webpack, gulp).

ci

Cambios en los archivos de configuración y scripts de Integración Continua (ej. GitHub Actions, Travis, CircleCI).

chore

Tareas rutinarias que no modifican el código fuente ni las pruebas (ej. actualización de versiones, tareas de mantenimiento de scripts).

revert

Se utiliza para revertir un commit anterior. El cuerpo del mensaje suele contener el hash del commit que se está revirtiendo.

📚 Ejemplos Reales

1. Commit básico con tipo y ámbito

feat(ui): agregar botón de modo oscuro

2. Commit completo con cuerpo y múltiples pies

fix: corrección de validación de usuarios

Se ha actualizado la lógica para permitir caracteres especiales en nombres.
Esto soluciona el problema reportado por soporte.

Reviewed-by: J. Doe
Refs: #456

3. Breaking Change (Dos variantes para el mismo cambio)

Opción A (Concisa): Usando ! en la cabecera para indicar impacto MAJOR.

feat(api)!: cambiar estructura de respuesta de error

Opción B (Explicativa): Usando el footer BREAKING CHANGE cuando se necesita detalle.

feat(api): cambiar estructura de respuesta de error

BREAKING CHANGE: la propiedad 'error' ahora devuelve un objeto en lugar de un string.
