Conventional Commits

The definitive guide to writing commit messages that both humans and machines can understand.

💡 Why is it important?

Writing a messy commit message is easy, but maintaining a project long-term is not. Conventional Commits offers a lightweight structure that allows:

  • Generate CHANGELOGs automatically.
  • Determine the next semantic version number (SemVer) without human intervention.
  • Help other developers understand the project history quickly.

🚀 Semantic Versioning (SemVer)

Conventional Commits and SemVer go hand in hand. The structure of your commit dictates how your software version should increment.

MAJOR . MINOR . PATCH

Example: If you are on version 1.0.0 and you make a feat: ... commit, the next version will be 1.1.0.

🧩 Message Anatomy

Hover over components to understand their function.

feat (api) ! : add token authentication

The body and footer of the message are optional and come after a blank line.

🏷️ Commit Types

Select a tab to see the basic types or the full Angular convention list.

BREAKING CHANGE MAJOR

A change that breaks compatibility. Indicated with ! after the type or with a BREAKING CHANGE: footer.

feat!: drop node 12 support
feat MINOR

Introduces a new feature to the code (feature). Equivalent to MINOR in SemVer.

feat: allow zoom on images
fix PATCH

Fixes a bug in the code. Equivalent to PATCH in SemVer.

fix: handle null user id

Although the specification allows any type, these are almost universally adopted.

docs

Changes affecting only documentation (README files, JSDoc comments, tutorials), without modifying functional code.

style

Format changes that do not affect code logic (whitespace, indentation, missing semicolons). Not to be confused with CSS styles.

refactor

A change to production code that neither fixes bugs nor adds features, but improves structure or readability.

perf

Changes specifically dedicated to improving system performance (algorithm optimization, reducing load times).

test

Addition of missing unit or integration tests, or fixing existing tests that were not working correctly.

build

Changes affecting the build system or external dependencies (e.g., npm, maven, gradle, webpack, gulp).

ci

Changes to Continuous Integration configuration files and scripts (e.g., GitHub Actions, Travis, CircleCI).

chore

Routine tasks that do not modify source code or tests (e.g., version updates, script maintenance tasks).

revert

Used to revert a previous commit. The message body usually contains the hash of the commit being reverted.

📚 Real Examples

1. Basic commit with type and scope

feat(ui): add dark mode button

2. Complete commit with body and multiple footers

fix: fix user validation

Updated logic to allow special characters in names.
This solves the issue reported by support.

Reviewed-by: J. Doe
Refs: #456

3. Breaking Change (Two variants for the same change)

Option A (Concise): Using ! in the header to indicate MAJOR impact.

feat(api)!: change error response structure

Option B (Explanatory): Using the BREAKING CHANGE footer when detail is needed.

feat(api): change error response structure

BREAKING CHANGE: the 'error' property now returns an object instead of a string.
